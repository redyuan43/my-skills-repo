# Audio Narration Script

将长文、Markdown、分析报告或笔记改写成适合朗读的中文讲解稿，并调用 `ssh ivan` 设备上的 Qwen3-TTS HTTP API 生成 WAV 音频。

## 自然语言触发

当用户没有显式输入 `$audio-narration-script`，但消息里出现以下意图时，也应该优先使用这个 skill：

- 想把文章、报告、笔记、Markdown 或长文改成音频稿、讲解稿、口播稿、朗读稿。
- 想生成讲解音频、朗读音频、播客独白或 WAV 文件。
- 出现“音频稿”“讲解音频”“口播稿”“生成 WAV”“朗读稿”“把这篇文章讲给我听”“把这个报告做成音频”等表达。

## 参考做法

这个 skill 借鉴通用音频脚本 skill 的成熟模式，但收窄为中文长文讲解稿：

- 先明确听众、时长、讲解形式，再改写正文。
- 把书面材料转成 spoken-word script，而不是直接清洗 Markdown。
- 为术语、英文缩写、数字和视觉内容做听觉友好的处理。
- 输出讲稿、发音/术语提示、分段建议，并生成完整 WAV 音频。

## 目标

输出应该像一个懂内容的人在给听众讲解，而不是机械朗读原文：

- 保留原文核心观点、结论、关键证据和必要数字。
- 把书面语改成自然口语，降低理解门槛。
- 用清晰的开场、过渡、总结和段落节奏组织内容。
- 对复杂概念补一句解释，对跳跃论证补一层承接。
- 避免夸张、鸡汤、营销腔和无根据扩写。

## 先确认的参数

如果用户没有指定，使用默认值直接推进；只有缺失信息会明显影响结果时才提问。

- **听众**：默认是对主题有兴趣、但不一定熟悉细节的普通中文听众。
- **形式**：默认是单人讲解；可改成播客独白、课程讲稿、短视频口播、财经/科技解读。
- **时长**：默认不强行压缩；如果用户给出目标时长，按约每分钟 250 到 320 个中文字估算篇幅。
- **风格**：默认清晰、稳重、有一点故事感；可改成更轻松、更专业、更适合小白、更像播客。
- **输出**：默认给完整讲稿和 WAV 音频；长文同时给大纲、完整稿、TTS 分块和 manifest。

## 输入处理

1. 如果用户给的是文件路径，先读取原文；如果是 Markdown，保留标题层级作为结构线索。
2. 如果原文很长，先提取：
   - 主题和听众可能关心的问题；
   - 3 到 7 个主线观点；
   - 关键事实、数字、人物、时间和因果关系；
   - 可以省略的目录、链接、图片说明、代码块、表格细节和重复段落。
3. 对表格和列表不要逐项念完，改成“先讲结论，再点关键差异”。
4. 对链接、脚注、图片路径、Markdown 语法、代码块，只在影响理解时转成口语解释。
5. 对“如图所示”“见表格”“代码如下”这类视觉依赖内容，改成听觉描述，或明确省略不影响主线的细节。

## 改写策略

按“讲给人听”的顺序组织，而不是死守原文段落：

1. **开场**：用 2 到 4 句话说明这篇内容在解决什么问题，以及听完能得到什么。
2. **主线**：把内容拆成若干小节，每节先给一句结论，再解释原因、例子和影响。
3. **过渡**：小节之间加自然承接，例如“理解了这一点，再看第二个问题就清楚了”。
4. **解释**：遇到术语时，用一句白话解释；遇到复杂机制时，用简单类比，但不要为了类比牺牲准确性。
5. **收束**：最后用 3 到 6 句话复盘最重要的结论，并指出听众下一步应该记住什么。

## 书面语到口语的转换

- “此外、因此、综上所述”可以改成“还有一点”“所以你会看到”“最后我们把它收一下”。
- 被动句优先改主动句，例如“这一点被验证了”改成“我们可以从这里看到这一点”。
- 长句拆短句；一段里不要连续堆三个以上抽象名词。
- 缩写第一次出现要展开，例如 API、ETF、ROI、GPU 这类词，先说清楚它指什么。
- 百分比、倍数、金额和日期要按听觉改写，例如“17.8%”可说成“接近百分之十八”。
- 引用和参考文献不要塞进正文朗读；保留关键来源名即可。

## 口播风格

默认使用“清晰、稳重、有一点故事感”的中文讲解风格：

- 句子短一些，一句话尽量只表达一个重点。
- 多用“我们先看”“这里关键是”“换句话说”“所以真正的问题是”这类口语承接。
- 避免连续堆叠长定语、括号和从句。
- 数字要适合听觉理解，例如把密集数字改成“约”“大概”“最关键的三个数字是”。
- 英文术语第一次出现时给中文解释；后面可使用简称。
- 避免“第三个风险，是费用。”这类短标题句独立成句，改成“第三个风险是费用，……”这种自然口语句。
- 不要加入“背景音乐”“停顿三秒”“音效”等制作指令，除非用户明确要求。

## 输出格式

默认先输出一个可朗读的 Markdown 讲稿：

```markdown
# 音频讲解稿：{标题}

## 开场
...

## 第一部分：...
...

## 第二部分：...
...

## 结尾总结
...
```

如果原文很长，先输出“讲稿大纲”，再输出完整讲稿。完整讲稿每段控制在 2 到 5 句，便于后续按段落切分 TTS。

生产级交付时，追加：

```markdown
## 术语与读法
- ...

## TTS 分段建议
- 第 1 段：开场到第一部分，约 ... 字
- 第 2 段：...

## 时长估算
- 约 ... 中文字
- 按每分钟 250 到 320 中文字估算，朗读时长约 ... 分钟
```

## 音频生成

默认始终生成音频。先把最终讲稿保存到输出目录中的 `narration_script.md` 和 `narration_script.txt`，再调用 bundled script：

```bash
python3 scripts/render_with_ivan_tts.py \
  --input narration_script.txt \
  --output-dir audio_output \
  --speaker serena
```

默认 TTS 端点：

- Gateway: `http://ivan-ms-7b17.taild500c8.ts.net:8091`
- 内部 worker: `http://127.0.0.1:8092` on `ssh ivan`，不要直接依赖它。
- 实测当前 gateway 后面是 2 个 Qwen3-TTS workers；脚本不要硬编码 worker 数，只要求 `workers_ready >= 1`。

可用环境变量：

- `IVAN_TTS_ENDPOINT`：覆盖 gateway endpoint。
- `NARRATION_TTS_CONCURRENCY`：默认 `2`，用于吃满当前 gateway 后面的两个 Qwen3-TTS workers；需要降低负载时可设为 `1`。
- `NARRATION_TTS_JOIN_SILENCE_MS`：合并音频时段间静音，默认 `180`。
- `NARRATION_TTS_MAX_RETRIES`：每段音频质量检查失败后的重试次数，默认 `3`。

脚本输出：

```text
audio_output/
├── manifest.json
└── narration_full.wav
```

脚本按自然语义句群分块。分块是为了绕开单次 TTS token/时长限制，默认只是内部临时文件，不作为交付物保留。需要排错时加 `--keep-chunks`，才会保留 `tts_chunks/` 和 `audio_chunks/`。默认并发为 2，用于吃满当前 gateway 后面的两个 worker；需要降低负载时显式设为 1。

TTS 前会做通用安全处理：

- 全大写英文缩写按字母读，例如 `ETF` 自动变成 `E T F`，不维护业务词表。
- “第几个风险，是……”这类短标题句会改成自然口语连接句，避免 Qwen3-TTS 生成半句后长静音。
- 每段 WAV 都做 QA：检测尾部长静音、内部长静音、全段近似静音；失败会自动重写或拆句重试。

## 质量检查

交付前检查：

- 是否没有丢掉原文的核心结论。
- 是否删掉了不适合朗读的 Markdown 噪声。
- 是否听起来像人在讲，而不是在念论文或报告。
- 是否没有捏造原文不存在的事实、数据、案例。
- 是否段落足够短，适合后续 TTS 分段。
- 是否把视觉依赖、密集表格、英文缩写和数字处理成听众能听懂的表达。
- 是否读一遍不会卡在过长句、绕口术语或突然跳转的逻辑上。
- 是否已经生成 `narration_full.wav`，并且 `manifest.json` 记录 endpoint、speaker、workers_ready、chunk 数、重试次数和音频 QA 结果。

## 可选交付物

默认交付：

- `narration_outline.md`：讲稿大纲。
- `narration_script.md`：完整讲解稿。
- `narration_script.txt`：去掉 Markdown 噪声的纯文本讲稿。
- `audio_output/narration_full.wav`：合并后的完整 WAV。
- `audio_output/manifest.json`：生成参数和分块元数据。
