# 发布操作手册

## 准备阶段

在执行变更前，先回答以下问题：

- 哪个仓库、分支、tag 或镜像 digest 是权威来源？
- 哪些目标需要更新，是否允许先选一个灰度节点？
- 现有部署命令、服务管理方式和健康检查是什么？
- 哪些路径保存状态、密钥或用户数据，必须避开？
- 已知正常版本是什么，回滚如何执行？

无法可靠回答时，先做只读检查，或向用户说明缺少的授权与信息；不要猜测生产路径或删除旧版本。

## 版本和激活

优先采用项目现有的版本化发布机制。若需要设计机制，release 应至少做到：

- 由不可变版本生成，能追溯到完整 commit SHA 或镜像 digest；
- 新 release 在激活前可完成依赖准备和基本检查；
- 运行服务只指向一个明确的 release；
- 旧的已知正常 release 在合理保留期内可用于回滚；
- 发布记录不包含机密。

多节点可以按两种常见策略执行：

- **灰度/滚动**：先更新一个节点，通过验收后逐台扩大范围。适合允许短时间版本不一致的服务。
- **预部署后激活**：所有节点先准备同一版本，全部成功后再依次激活。适合更强调版本一致性的独立边缘节点。

选择项目已验证的策略。任何节点的预部署、激活或健康检查失败时，停止继续扩散；是否回滚已成功节点取决于项目的可用性要求和用户指示。

## 验收

发布后至少验证：

- 服务进程、容器或 worker 处于预期运行状态；
- 健康检查或版本接口可访问；
- 运行版本与计划部署的版本一致；
- 关键业务路由仍按预期工作，尤其是鉴权边界；
- 多个被要求版本一致的节点返回相同版本。

健康检查成功不代表业务验收充分。对认证、消息、录音、文件处理等高风险改动，增加针对改动面的低风险契约检查。

## 故障与回滚

当发布后服务不健康：

1. 停止继续向其他节点发布。
2. 保存必要的非敏感状态、错误码和日志位置。
3. 回滚受影响节点到已知正常版本。
4. 重新运行状态与健康检查。
5. 在汇报中区分“已恢复服务”与“根因已修复”。

禁止用临时手工编辑运行目录替代可追溯修复。紧急修复应在恢复服务后回写到权威代码仓库和发布流程。

## 最终汇报

用简洁事实说明：

- 权威来源：PR、提交或 tag。
- 实际发布版本：tag、完整 commit SHA 或镜像 digest。
- 范围：已更新和未更新的目标。
- 验证：测试、健康检查与关键契约检查。
- 回滚：是否发生、影响范围与最终状态。
- 风险：尚未验证的设备、功能或外部依赖。
