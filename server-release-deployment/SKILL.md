# Server Release Deployment

将服务端发布视为一个可恢复的版本切换，而不是把工作目录直接复制到机器上。先读取目标仓库的 `AGENTS.md`、部署文档和现有脚本，确认权威代码来源、目标环境、状态目录和健康检查方式。

## 关键约束

- 代码来源必须明确。优先部署已合并的权威分支、发布提交或 tag；不要把未提交的工作树作为生产版本。
- 每次发布必须能定位到不可变的版本标识，例如 tag、完整 commit SHA 或镜像 digest。
- 代码 release 与运行时状态分离。数据库、用户数据、设备绑定、上传文件、密钥和环境配置不得随代码发布在不同节点间复制。
- 只有用户明确要求发布、部署、更新或回滚时，才执行会改变远端服务或重启进程的操作。实现、审查或准备阶段止于测试和发布说明。
- 不打印或写入令牌、密码、私钥、生产配置或用户数据。

## 标准流程

1. **识别发布模型**：确认权威仓库/分支、目标节点、服务管理方式、持久化状态位置、健康检查端点和现有发布脚本。优先复用项目已有脚本。
2. **准备版本**：完成变更，运行与风险相称的测试，并将可发布代码合并到权威来源。记录将要部署的完整版本标识。
3. **发布前检查**：确认目标节点可达、磁盘和服务状态正常、当前 release 可识别；明确发布范围是单节点灰度还是全量。
4. **部署与激活**：让每个目标从同一不可变版本安装代码。多节点发布优先先完成预部署，再按项目既有策略滚动激活；每一步失败即停止扩大范围。
5. **验收**：检查进程或容器状态、健康接口、版本标识与核心鉴权/业务契约。多个应运行同版本的节点必须报告相同版本。
6. **回滚**：若激活后健康检查失败，优先使用上一个已知正常 release 回滚受影响节点，再收集日志分析；不要直接编辑生产运行目录救火。
7. **汇报**：说明权威提交/PR、发布版本、已操作节点、测试与验收结果、回滚情况和剩余风险。

## 多节点边缘服务

相同程序不等于共享数据。若每台边缘设备各自服务不同的终端或用户，保持代码版本一致即可；数据库、设备绑定和本地文件仍应隔离。只有用户明确设计了共享控制面或数据同步时，才把跨节点通信加入发布方案。

## 项目配置

具体项目应把仓库路径、权威分支、节点别名、部署命令、健康检查与回滚命令记录在仓库的 `AGENTS.md` 或项目发布文档中。需要建立或审查这类项目配置时，阅读 [项目发布配置模板](references/project-release-profile.md)；需要较完整的操作与验收标准时，阅读 [发布操作手册](references/release-playbook.md)。
